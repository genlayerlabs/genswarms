운영체제라고 생각해 보세요.

운영체제는 직접 만들지 않은 프로그램을 실행합니다. GenSwarms는 에이전트를 그렇게 실행합니다. 시작하고, 격리하고, 메시지를 라우팅하고, 실패하면 재시작합니다.

모든 에이전트는 프로세스입니다.

각 에이전트는 자기 샌드박스 안에서, 자기 슈퍼바이저 아래 실행됩니다. 하나가 크래시되면 그 에이전트는 재시작되고, 나머지는 계속 일합니다. 역할, 모델, 실행 위치는 따로 정합니다.

여기서부터 그림은 스웜 하나를 따라갑니다. Telegram에서 고객에게 답하는 지원팀입니다.

작동 방식.

운영체제의 구성 요소별로 GenSwarms가 채워 넣은 것.

프로세스
에이전트마다 슈퍼바이저가 관리하는 OTP 프로세스. 역할, 모델, 백엔드는 따로 설정.
격리
에이전트별 bwrap, Docker 또는 Apple container.
네트워크
격리된 에이전트는 자기 모델 엔드포인트에만 접근.
메시지
선언된 경로로만, 홉마다 검사.
서비스
오브젝트: 같은 그래프 위의 결정적 코드.
드라이버
Local, Tmux, Docker, Apple container, SSH, Bwrap, Mock.
패키지
gsp와 swarmidx: 서명, 콘텐츠 주소 지정, 로컬 머신에서 검증.
상태
시드와 변경 로그. 잘못된 변경은 거부. 데이터베이스에서 복원.
제어
REST, WebSocket, CLI, 코딩 에이전트용 스킬 파일.
이벤트
모든 메시지, 크래시, 재시작을 실시간으로.

LangGraph, CrewAI, AutoGen과 무엇이 다른가요?

프레임워크는 사용자 코드 안에서 에이전트를 구성합니다. GenSwarms는 각 에이전트를 슈퍼바이저가 관리하는 별도 프로세스로 실행합니다.

GenSwarms와 LangGraph, CrewAI, AutoGen 비교
질문genswarmsLangGraphCrewAIAutoGen
무엇인가각 에이전트를 슈퍼바이저가 관리하는 프로세스로 실행하는 런타임상태를 가진 에이전트를 위한 오케스트레이션 프레임워크이자 런타임. LangSmith Deployment에서 호스팅에이전트 크루와 플로우를 위한 오픈소스 프레임워크. AMP로 배포멀티 에이전트 프레임워크, 현재 유지보수 모드. 후속은 Microsoft Agent Framework
에이전트가 실행되는 곳각자 슈퍼바이저가 관리하는 별도 프로세스에서: 로컬, 샌드박스, 컨테이너 또는 SSH사용자의 Python 또는 JS 프로세스 안, 혹은 LangSmith Deployment 서버사용자의 Python 프로세스 안, 혹은 CrewAI AMP 관리형 인프라사용자의 프로세스 안, 혹은 실험 단계인 분산 런타임으로 여러 워커에 걸쳐
크래시의 영향 범위크래시가 난 그 에이전트. 슈퍼바이저가 재시작해당 실행(run). 체크포인트로 재개할 수 있고, 노드는 재시도 가능해당 실행(run). 에이전트는 오류 시 재시도하고, 플로우는 상태를 저장해 재개 가능사용자 코드가 처리. 팀 상태는 저장했다가 다시 불러오기 가능

각 프로젝트의 공식 문서 기준, 2026년 9월.

보장하는 것, 아직 보장하지 않는 것.

현재 0.2.0에 포함된 것과 알려진 한계.

보장하는 것

  • 크래시가 나면 스웜이 아니라 에이전트 하나만 재시작.
  • 메시지는 선언된 경로로만 이동.
  • 잘못된 설정과 변경은 실행 전에 거부.
  • 패키지는 서명된 로그와 대조해 검증.

아직 보장하지 않는 것

  • 운영자 토큰은 하나뿐, 사용자별 역할은 없음.
  • 최소 한 번 전달, 정확히 한 번은 아님.
  • 비용 예산은 코어가 아닌 패키지로 제공.
  • 패키지를 업데이트하면 에이전트가 재시작됨. 실행 중 교체는 아직 없음.
  • 스웜당 에이전트 기본 100개 (설정 가능).

한 팀으로 시작하세요. 에이전트 수천 개로 확장하세요.

현재 채팅 어시스턴트, 코딩 에이전트, 트레이딩 시뮬레이션, 다른 스웜을 지켜보는 스웜에 쓰이고 있습니다.
